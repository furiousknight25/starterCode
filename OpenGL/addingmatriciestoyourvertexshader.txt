Connecting the Matrices to Your Shader - Step 2

We now need to modify your vertex shader. I would strongly suggest you make a copy of vertexShader_passthrough.glsl to a new shader file that you will use to better support vertex processing. Let's call it

vertexShader_withMatrixTransformation.glsl

You will want to modify your vertex shader to look like this:

#version 330 core

layout(location=0) in vec3 in_Position;
layout(location=1) in vec3 in_Color;

uniform mat4 projMatrix;
uniform mat4 viewMatrix;

out vec3 color;

void main(void)
{
  color = in_Color;
  gl_Position = projMatrix * viewMatrix * vec4(in_Position, 1.0);
}

There are a couple of things to notice here:

    Uniform variables that represent the two matrices we will need to use within the shader.  Read the last bullet below for more detail in Uniform variables.
    Multiplication of the in_Position by these matrices to transform the vertex to the canonical view volume.

As a bit of recap, Section 17.12 contains the details for these new shaders.  Here are some key points for each:

    Shaders create variables with different declaration types. In our current shaders, you see layout, in, out, and uniform. Variables that are declared without these keywords are local variables to the shader.  You may want to re-read Section 17.8 for a review of these terms too.
    The layout constructs in the shader code determine the incoming and outgoing data.  For the vertex shader, we now have two sources of incoming data: the positions (location or attribute=0) and the color (location or attribute 1). These are both vec3 and have been given a unique variable name for use in the shader code.  
    The in and out variable declaration determine what the shader will send (out) to the next shader or receive from (in) the previous shader. In this way, a vertex shader can pass or share data with the fragment shader that follows it. This is an important concept to understand because this is HOW per-vertex data is sent to the fragment shaders.  The fragment shader system on the graphics card will use barycentric interpolation to determine the exact value at each fragment using the alpha, beta, and gamma parameters of the fragment.  So if a color is set at each vertex, the color will be interpolated at each fragment in the fragment shader.
    The uniform declarations are variables that are communicated from the host (your CPU code) to the device.  So this means that we will copy the projection matrix and the camera matrix from the host to the device before we run the shader. Uniform variables are the primary mechanism to send in different data types, from ints, floats, vec3, mat4, etc... from your host code to the device with GLSL.

 
Adding Code to Copy the Matrices to Your Shader - Step 3

There are a couple steps you need to do this.  We have a shader that has uniform variables for a projection matrix (projMatrix) and a view or camera matrix (viewMatrix).  On the host, we need to get a handle to these uniform variables so that we can copy data into them from the host.

To get a handle to your uniform variables, you will use my GLSL shader code to get this reference. If you're interested in the underlying call, feel free to look at GLSL.[h,cpp].  Since we called our variables projMatrix and viewMatrix, we can use those names to get handles to those variables in the shader.

For example, in you code. right after you load the shaders and call "createProgram" in my GLSL interface, you will need to make the following call to get the identifier that refers to the projMatrix variable in the shader:

GLint projMatrixID = shader.createUniform("projMatrix");

The call to createUniform can be used to get a reference to any uniform variable in the shaders if you want to communicate host data to the device shaders. Once the shader program is created, you can get a handle to the uniform shader variables.  

Here is the complete example including the loading of the shaders:

  // Create a shader using my GLSLObject class                                                                                                       
  sivelab::GLSLObject shader;
  shader.addShader( "vertexShader_withMatrices.glsl", sivelab::GLSLObject::VERTEX_SHADER );
  shader.addShader( "fragmentShader_barycentric.glsl", sivelab::GLSLObject::FRAGMENT_SHADER );
  shader.createProgram();

  GLuint projMatrixID, viewMatrixID;
  projMatrixID = shader.createUniform( "projMatrix" );
  viewMatrixID = shader.createUniform( "viewMatrix" );

// create the view matrix from our camera data                                                                                                   
glm::mat4 M_view = glm::lookAt( m_pos, m_pos - m_W, m_V );

/* Render your objects here */
shader.activate();

// copy from the host to the device the view matrix and the projection matrix                                                                                       
glUniformMatrix4fv(projMatrixID, 1, GL_FALSE, glm::value_ptr( M_ortho ));

glBindVertexArray(m_VAO);
glDrawArrays(GL_TRIANGLES, 0, 3);
glBindVertexArray(0);

shader.deactivate();

In this step there are some things to note:

    We use GLM's lookAt function to create the View or Camera Matrix for us (M_view).  We could have constructed it on our own but this is a nice function to help us create that matrix. The function takes the position of the camera as the first argument, the point in space where the camera is looking (m_pos - m_W gets us that location), and the Up vector from the camera. Note that we hard-coded the camera here as the default, but your camera classes have everything you need to generalize this to any view.  More info on GLM's functions can be found here: OpenGL GLM Documentation Page
    We also use OpenGL functions (glUniform*) to copy different types of data from the host to the device. In this case, we copy a Matrix 4. We use the Uniform variable handles we got previously to copy the different matrices to the GPU.  More information on the many glUniform function calls can be found here: Link to OpenGL glUniform Documentation
    Specifically, the glUniformMatrix4fv call we made here needs the uniform variable handle as the first argument, the size of the type (in this case just 1) as the second argument, whether to automatically transpose the matrix (FALSE in this case -- we want the matrix as is when we copy it), and a pointer to the data to copy as the fourth argument, which we get by using GLM's value_ptr function.
