Q: Write down the set of tests you came up with that ensures that your sphere code behavior is correct AND that you can be confident it is correct going into any future changes. Be sure to describe the behavior you expect and how will verify it.
A: We implemented a thorough test suite in `utests/utest_sphere.cpp` containing 9 test cases with 31 assertions:

   1. Sphere Construction and Attributes:
      - Expected Behavior: Default constructor creates a unit sphere (radius 1.0) centered at the origin (0, 0, 0). Parameterized constructor correctly sets center and radius.
      - Verification: Checked coordinates and radius with REQUIRE against expected values.

   2. Direct Central Hit (Hit - Discriminant > 0):
      - Expected Behavior: A ray shot directly along any axis passing through the sphere's center must intersect the sphere at two distinct points.
      - Verification: Evaluated rays along -z, +z, -x, and -y; verified `intersect(r) == true`.

   3. Off-Center Piercing Hit (Hit - Discriminant > 0):
      - Expected Behavior: A ray parallel to an axis or diagonal whose perpendicular distance to the sphere center is less than the radius must intersect.
      - Verification: Offset ray at distance sqrt(2) for radius 2.0 sphere and diagonal ray; verified `intersect(r) == true`.

   4. Tangent / Grazing Ray (Hit - Discriminant == 0):
      - Expected Behavior: A ray whose line passes at a distance exactly equal to the radius grazes the surface with a single intersection point (discriminant = 0).
      - Verification: Tested rays at exactly x = radius and y = -radius; verified `intersect(r) == true`.

   5. Clear Miss (Miss - Discriminant < 0):
      - Expected Behavior: A ray passing outside the sphere radius or pointed away into empty space has no real roots.
      - Verification: Rays offset beyond radius (e.g., x = 1.5, y = 2.0 for unit sphere) and shooting away; verified `intersect(r) == false`.

   6. Sphere Behind Ray Origin (Miss - Negative t roots):
      - Expected Behavior: A ray pointing away from a sphere behind it has geometric line roots where t < 0. Because rays only travel forward (t >= 0), it must not count as an intersection.
      - Verification: Ray starting at (0, 0, 5) pointing towards +z away from sphere at origin; verified `intersect(r) == false`.

   7. Ray Origin Inside Sphere (Hit - t1 < 0, t2 > 0):
      - Expected Behavior: A ray starting inside the sphere (at center or off-center) pierces the surface from the inside on its forward path.
      - Verification: Rays originating at (0, 0, 0) and (0.5, -0.5, 0.5) inside a radius 2 sphere; verified `intersect(r) == true`.

   8. Translated Sphere Position:
      - Expected Behavior: A sphere placed at non-origin coordinates (e.g., (5, 5, -5)) correctly computes intersection relative to its new position.
      - Verification: Ray aimed at translated center returns `true`; ray aimed at old origin returns `false`.

   9. Polymorphic Shape Interface & Backward Compatibility:
      - Expected Behavior: Calling `intersect` through abstract `const Shape*` or `const Shape&` correctly resolves via virtual dispatch. `Circle` operates identically as a derived sphere.
      - Verification: Tested hit and miss rays through Shape pointer, reference, and Circle object.

Q: What's different and better with this example?
A:
1. Dynamic Polymorphism & Scene Abstraction: The first snippet hardcodes a single concrete shape (`Circle s` or `Sphere s`) directly inside the pixel loop. The improved snippet stores shapes in a polymorphic container (e.g. `std::vector<std::shared_ptr<Shape>>` or a `Scene`/`hittable_list`) and invokes the virtual `intersect()` method polymorphically on each object.
2. Extensibility (Open/Closed Principle): New geometric primitives (triangles, planes, boxes, meshes) can be added simply by creating new derived classes from `Shape` without modifying the rendering loop.
3. Multi-Object Scenes and Depth/Occlusion Handling: In scenes with multiple overlapping objects, the advanced loop tracks the *closest* valid hit along the ray ($t_{\min} < t < t_{\max}$), ensuring that objects in front occlude objects behind them.
4. Rich Hit Records (`hit_record`): Instead of returning only a binary `bool`, the improved approach records hit information (intersection point $P$, surface normal $\mathbf{N}$, parameter $t$, and material pointer), enabling realistic shading, reflections, refractions, and lighting.
5. Separation of Concerns: Decouples scene definition from ray generation and image rasterization.

### Camera Declaration

Camera declaration in `examples/SphereRender.cpp`:
```cpp
const float aspect_ratio = 5.0f / 3.0f;
const int image_width = 600;
const float focal_length = 1.0f;
const float viewport_height = 2.0f;

// Camera setup: Centered at origin looking along the -z axis
const point3 camera_position(0.0, 0.0, 0.0);
const vec3 camera_rotation(0.0, 0.0, 0.0);

perspective_camera cam(image_width, aspect_ratio, focal_length, viewport_height, camera_position, camera_rotation);
```

class perspective_camera : public camera {

    float focal_length = 1.0f;

    // Orthonormal basis vectors

    vec3 w = vec3(0, 0, 1); // camera backward (opposite to forward look direction)

    vec3 viewport_u;
    vec3 viewport_v;
